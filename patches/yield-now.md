- **Grund:** ZehOS #716. `Thread.Yield` setzte nur `_needReschedule`; gewechselt wurde erst am nächsten Hardware-IRQ-Austritt, ohne Gerätelast am Timertakt. Ein Ping-Pong zweier Threads über Yield kostete so eine Zeitscheibe je Wechsel, im Kernel wie aus einem Systemaufruf (Ring 3, #634 `aswitch`). Jetzt löst `YieldThread` wie `Park` die Selbst-IPI (`TryRaiseReschedule`) aus, deren Austritt sofort wechselt, aber nur, wenn in der Laufstruktur der eigenen CPU ein anderer Thread wartet (`GetRunQueueCount` unter der Queue-Sperre); sonst bleibt es beim Flag wie bisher. Ein Wecken, das danach einen Thread hier einreiht, sendet die IPI selbst. Flag und IPI werden unter maskierten Interrupts auf der dabei gelesenen CPU gesetzt (der Aufrufer kann seit dem Lesen der CPU-ID umgezogen sein; kein Handler schreibt dazwischen ins ICR). Nur mit Interrupts an: Ein maskierter Aufrufer (Handler, maskierter Abschnitt, IST-Handler für #DF/NMI/#MC) setzt wie bisher nur das Flag, damit nie von einem solchen Rahmen weggewechselt wird. Im Systemaufruf läuft der Handler mit Interrupts an auf dem Kernelstapel des Threads (`__managed__user_syscall`); die IPI landet dort wie jeder Timertakt, oder nach `sysretq` beim ersten Ring-3-Befehl. Ein Prüfpunkt im Syscall-Rückweg ist deshalb nicht nötig. Blockieren (`Park`) wechselte schon sofort. Neue Schnittstelle `PerCpuState.SwitchIsYield`: `YieldThread` merkt sich den abgebenden Thread je CPU, wenn es sofort wechselt (ein anderer Thread wartet; sonst kein Merker, damit der nächste Tick oder ein Wecken nicht als Yield zählt; ein maskierter Aufrufer merkt sich ihn immer, der Wechsel kommt dann am nächsten Interrupt-Austritt), der nächste Wechsel auf dieser CPU setzt das Flag für `PickNext` und `OnThreadYield`, wenn er genau diesen Thread noch laufend abnimmt. Grund: Der Yield wechselt jetzt, bevor ein Tick die Scheibe belastet hat; eine Policy, die einen verdrängten Thread vorn mit Restscheibe zurückstellt (ZehOS-Klassenscheduler), gab einem Thread, der in einer Schleife abgibt, sonst jede Runde seiner Klasse, und Threads hinter ihm liefen nie (Story Ladybird, KVM smp1, Probe `aswitch`).
- **Grenzen:** Ist auf der CPU sonst nichts eingereiht, kehrt der Yield sofort zurück (keine Interrupt-Runde je Spin in CoreLibs Spin-then-block, bis zu etwa 70 Yields); dafür kostet jeder Yield eine Sperrrunde der eigenen Queue-Sperre. Threads auf anderen CPUs zählen nicht. Die Prüfung nutzt den Diagnose-Haken `IScheduler.GetRunQueueCount`; eine Policy muss ihn korrekt liefern. `RhYield` gibt weiter 0 zurück. ARM64 (SGI) nicht im Gast geprüft.
