# gc-oom-throw

- **Commit:** Squash des PRs gegen `cosmos`
- **Dateien:** `src/Cosmos.Kernel.Core/Runtime/Memory.cs`, `src/Cosmos.Kernel.Core/Internal/Runtime/CompilerHelpers/LibraryInitializer.cs`, `tests/Kernels/Cosmos.Kernel.Tests.GarbageCollector/Kernel.cs`
- **Grund:** Die Allokationshelfer (`RhpNewFast`, `RhpNewArray`, `RhpNewArrayFast`, `RhpNewPtrArrayFast`, `RhAllocateNewArray`, `RhAllocateNewObject`, `RhNewString`, `RhNewObject`, `RhpNewFinalizable`, Boxing) gaben bei erschöpftem Heap `null` zurück (`GarbageCollector.AllocObjectSlow` nach Refill, Collect, Refill). Vom Compiler erzeugter Code prüft das Ergebnis von `newobj`/`newarr` nie: Ein Zugriff wurde zum Page Fault an kleiner Adresse (ZehOS E4.0-Lauf 10, CR2=0x10), ein Span darüber zu stillem Datenverlust („Destination is too short“, ZehOS #530: `new byte[46.9 MB]` im TCP-Puffer). Jetzt wie .NET: Fehlschlag wirft `OutOfMemoryException`. Dazu zwei Fehler derselben Stelle: Die Arraygröße `BaseSize + length * ComponentSize` lief in 32 Bit über (`new long[2^29 + 1]` wurde ein 40-Byte-Objekt mit Length 2^29 + 1, Schreiben ging in fremde Objekte); sie wird in 64 Bit gerechnet, über `int.MaxValue` gibt es `OutOfMemoryException` (Grenze wie .NET knapp unter 2 GB, hält auch `Align` und Größenklassen in 32 Bit). Negative Länge gab `null`, jetzt `OverflowException` wie `RhpNewArray` in .NET. Die Ausnahme wird frisch angelegt (eine geteilte Instanz sammelte bei jedem Wurf den Stacktrace weiter); scheitert schon das oder legt eine andere CPU gerade ihre an, wird eine beim Start (`LibraryInitializer`, nach `InitializeModules`) angelegte Instanz geworfen, deren Stacktrace vorher geleert wird. Ohne diese Reserve ginge das gescheiterte `new` endlos in den Wurf zurück. Vor dem Anlegen der Reserve hält ein verschachteltes OOM mit `FailFast` an. Der Weg ohne GC (`MemoryOp.Alloc`, nur vor `GarbageCollector.Initialize`) bleibt unverändert. `GarbageCollector.AllocObject` selbst liefert weiter `null` (interne Schnittstelle, einziger Aufrufer `Memory.AllocObject`); geworfen wird außerhalb der Interruptmaske.
- **Null-Prüfer (bewertet):** Cosmos: `ManagedModule.cs` (GC-Statikbasen, `obj is null` -> `OutOfMemoryException`) wird toter Zweig, bleibt als Abwehr für den Weg ohne GC; `CoreLib` `GC.AllocateNewArray`/`RuntimeHelpers.GetUninitializedObject` prüfen `null` selbst und werfen dieselbe Ausnahme, jetzt nur früher; `Boxing.RhBox` und alle `newobj`/`newarr` prüften nicht (Page Fault statt Ausnahme). ZehOS: `Shared/BufferAllocation.TryAllocate` (fängt `OutOfMemoryException` schon, `IsMissing` wird toter Zweig), `Storage/FileService` (`AllocateBuffer` über `TryAllocate`), `Runtime/Wasm/WasmSaveStore`, `Storage/CosmosExt2RootProbe` (Probe, fängt `OutOfMemoryException`), `Storage/Migration/MigrationJournal` (Kommentar), `Scheduling/ThreadStarter` (fängt `OutOfMemoryException`): alle bleiben korrekt; die Null-Zweige können nach dem ZehOS-PR entfallen.
- **Entfernter ZehOS-Umweg:** keiner sofort; die Null-Abwehr in `BufferAllocation` wird überflüssig (Nachzug nach Merge).
- **Prüfung:** Cosmos-Bau (`scripts/build-cosmos.sh`); GC-Testkernel `GC_OutOfMemory_HeapExhaustedThrows`, `GC_OutOfMemory_SizeOverflowThrows`, `GC_NegativeArrayLengthThrowsOverflow`; ZehOS Hosttests, nativer Bau, Desktop KVM SMP leer/4.
