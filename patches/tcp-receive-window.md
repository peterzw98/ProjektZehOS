# tcp-receive-window

- **Commit:** Squash von #537 (`4eeb0f92`)
- **Dateien:** `src/Cosmos.Kernel.System/Network/Protocols/Tcp/TcpConnection.cs`, `tests/Cosmos.Kernel.Tests.System/Network/Protocols/Tcp/TcpConnectionTest.cs`
- **Grund:** ZehOS E5-O (#530), Doom-WAD-Download über HTTPS mit `bad_record_mac`. Zwei Fehler im Empfangspfad:
  1. **Keine Flusskontrolle.** `TCB.RcvWnd` blieb fest bei `TcpWindowSize` (32 KiB), egal wie viel ungelesen im Puffer lag. Liest die Anwendung langsamer, als das Netz liefert, wächst `_data` ohne Grenze (im Gast 23 MB ungelesen); die nächste Verdopplung (`new byte[46,9 MB]`) scheiterte, und `AppendToData` warf (`Destination is too short`). Jetzt hält eine Verbindung höchstens `ReceiveBufferLimit` (256 KiB) ungelesen, das angebotene Fenster ist der freie Platz darunter (höchstens 32 KiB), die Verdopplung endet an der Grenze. Die rechte Fensterkante (`RcvNxt + RcvWnd`) wandert nie zurück. Hebt ein `ReadData` das Fenster von unter auf mindestens die Hälfte von `TcpWindowSize`, geht einmal ein Window-Update (ACK) hinaus; sonst wartete die Gegenstelle auf ihren Persist-Timer. Die Fensterprüfung in `OnPacketReceived` lässt ein Segment jetzt bis genau an die Kante zu (`<=` statt `<`): mit schrumpfendem Fenster wies `<` das Segment ab, das es genau füllt, und bei Fenster null jedes reine ACK und FIN bei `RcvNxt`.
  2. **ACK für verlorene Daten.** `ProcessEstablished` erhöhte `TCB.RcvNxt` vor `AppendToData`. Warf das Anhängen, fing `KitNetworkConsumer.OnReceive` die Ausnahme; das Segment war verloren, `RcvNxt` aber weiter, und das nächste ACK bestätigte die verlorenen Bytes. Die Gegenstelle wiederholte sie nie, der Datenstrom hatte eine Lücke. Jetzt wird erst angehängt, dann `RcvNxt` erhöht; `AppendToData` ändert beim Wurf keinen Zustand (alle Zuweisungen nach den Kopien), das Segment bleibt unbestätigt und kommt als Wiederholung.
- **Offen, nicht in diesem Patch:** Der GC (`GarbageCollector.AllocObjectSlow`) gibt bei Speichermangel `null` zurück statt `OutOfMemoryException` zu werfen; eigener Block.
- **Entfernter ZehOS-Umweg:** keiner
- **Prüfung:** Hosttests `TcpConnectionTest` (neu: `ReceiveWindow`, `ReceivePath` über `ReceiveData`: Wurf beim Anhängen lässt `RcvNxt` stehen, Segment bis genau an die Kante, Grenze ohne Fenster; mit dem alten Code rot); Cosmos-Bau (`scripts/build-cosmos.sh`); ZehOS nativer Bau und Doom-WAD-Download über HTTPS (KVM, SMP 8c4t2)
