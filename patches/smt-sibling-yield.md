# smt-sibling-yield

- **Commit:** Squash des PRs (Hash beim Merge); Basis `cosmos` 6b28fc44
- **Dateien:** `src/Cosmos.Kernel.Core/Scheduler/IVoluntaryMove.cs` (neu), `src/Cosmos.Kernel.Core/Scheduler/SchedulerManager.cs`, `src/Cosmos.Kernel.Core/Scheduler/PerCpuState.cs`, `src/Cosmos.Kernel.Core/PublicAPI.Unshipped.txt`
- **Grund:** Ein laufender Thread verlässt seine CPU heute nur, wenn er blockiert, endet oder seine Menge die CPU ausschließt. `Balance` zieht nur Wartende. Ein Rechenthread, der nie blockiert, bleibt daher neben einem belegten SMT-Geschwister, auch wenn inzwischen ein ganzer Kern frei ist. ZehOS #674 hat das gemessen (Messung A, KVM mit auf Host-SMT-Paare gepinnten vCPUs): Bei durchsatzgebundener Last dauert die Rechnung neben einem belegten Geschwister doppelt so lange (186–192 gegen 93–111 ms). Der Patch öffnet eine Schnittstelle, keine Policy. Die neue optionale Schnittstelle `IVoluntaryMove` wird einmal beim Setzen des Schedulers erkannt. Fehlt sie, ändert sich nichts. Implementiert die Policy sie, fragt der Tick der CPU, die den Thread rechnet, alle `VoluntaryMoveIntervalTicks` (10 Ticks) `SelectMoveTarget`. Die Frage geht ohne Sperre wie bei `Balance` und nur für einen laufenden Nicht-Idle-Thread, dessen effektive Menge noch eine andere CPU enthält. Eine gültige Antwort (eine andere CPU der Menge) nimmt den Thread beim Wechsel desselben Interrupt-Ausgangs herunter, über den vorhandenen Verdrängungsweg (`_pendingMigration`, `MigratePending`, `MigrateLocked(evicting: true)`, Reschedule-IPI). `MigratePending` nimmt dann das genannte Ziel, solange die Menge es erlaubt, und prüft es unter beiden Sperren erneut: Läuft dort inzwischen etwas anderes als der Idle-Thread oder steht ein Reschedule an, ist das Ziel veraltet, und der Thread bleibt wie nach einer Verdrängung auf dieser CPU. Die Affinität wird nie geändert, `IdealCpu` folgt wie bisher nur einer erzwungenen Bewegung.
- **Entfernter ZehOS-Umweg:** keiner (bisher keine Gegenmaßnahme, nur die Grenze aus #659)
- **Prüfung:** Stand Entwurf: `Cosmos.Kernel.Core` Release gebaut, keine neue Warnung in den geänderten Dateien. Gast, Testkerne und Messung offen.
- **Grenzen:** Gegen Pendeln sorgt die Policy. Der Mechanismus prüft nur, dass das Ziel frei ist. Ein veraltetes Ziel kostet eine Platzierung, keine Korrektheit. Ein Thread im Zustand `Created` wird nie bewegt (nur `Running`).
