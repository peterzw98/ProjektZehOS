# fat-inode-cache

- **Commit:** Squash von PR <PR-Nummer> (`<Hash>`), nach Merge einzutragen; geschrieben auf `origin/cosmos` 6b28fc44
- **Dateien:** `src/Cosmos.Kernel.System/FileSystem/Fat/FatInodeCache.cs` (neu), `FatSuperblock.cs` (`GetOrCreateInode`, `AllocateDirectoryEntry`, `RemoveDirectoryEntry`, `UpdateInodeEntry`, `ForgetInode`, `Drop`); Tests `tests/Cosmos.Kernel.Tests.System/FileSystem/Fat/FatInodeCacheTests.cs`
- **Grund:** `FatSuperblock._inodeCache` hielt jedes Inode einer nichtleeren Datei bis zum Aushängen. Die verteilten kleinen Objekte ließen keinen zusammenhängenden Block mehr frei: OOM beim Lesen von 8.300 von 100.000 Dateien, mit 512 MiB 3/3 und mit 1 GiB 3/3 (ZehOS #672)
- **Änderung:** Der Cache hält Inodes nur noch schwach (GC-Handle je Startcluster). Solange eine Handle, eine Auflistung, ein Kind (`Parent`) oder eine laufende Operation das Inode hält, liefert ein Lookup dasselbe Objekt; danach entsteht es neu aus dem Verzeichniseintrag. Tote Einträge werden ab 1024 Einträgen (danach ab dem Doppelten der lebenden) ausgeräumt. Eine Monitorsperre schützt nur die Buchführung (innerste Sperre, kein Plattenzugriff darin); Operationen auf dem Volume serialisieren weiter die Aufrufer
- **Warum nicht wie `ext2-inode-cache-evict` (Grenze, `Dirty`, `Detached`):** Das FAT-Inode hat keinen Zustand, der nur im Cache liegt. Ist es neuer als sein Eintrag, hält es die Handle
- **Geändertes Verhalten:** Wird ein Inode nicht mehr gehalten, baut der nächste Zugriff die Clusterkette neu auf (Mehrkosten nicht gemessen). Sonst keines
- **Entfernter ZehOS-Umweg:** keiner
- **Grenzen:** Schlüssel bleibt der Startcluster; leere Dateien haben weiter ein Objekt je Öffnen. Nach dem Kürzen auf 0 bleibt der alte Schlüssel stehen, bis der Cluster neu vergeben wird (wie vorher). Nicht behoben und schon vorher vorhanden: eine offene, umbenannte Datei kann einen fremden Verzeichniseintrag überschreiben (#702)
